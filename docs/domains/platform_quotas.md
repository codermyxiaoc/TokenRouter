# 用户平台额度

本文描述用户在十五个平台上的日、周、月 USD 额度，从注册默认值、请求预检查到资金事务内的数据库计数。它不描述上游账号套餐额度、订阅计划窗口或 API Key 自身限速。

- [一致性与升级](#一致性与升级)：排查统计差异、多实例或升级基线时读取。

## 额度模型

每个用户和平台最多一条 `user_platform_quotas` 活跃记录。允许的平台为 Anthropic、OpenAI、Gemini、Antigravity、Grok、Qoder、Kimi、Zhipu、DeepSeek、MiniMax、OpenCode、独立 Video、TypeSafe、Cline 和 Command Code。每条记录分别保存日/周/月 limit、usage 和 window start。国产供应商的 payg/coding 只是上游账号模式，用户额度仍按各自平台归属，不拆成额外平台。OpenCode 的 Zen/GO 同样共用 `opencode_go` 额度；Video 的四家协议共用 `video` 平台额度，不占用 MiniMax 文本或历史 Seedance 的 OpenAI 额度。迁移 277、289 与 297 只扩展允许的平台（保留数据库 CHECK 与旧平台），不写入无限额记录。

limit 的三态语义是领域不变量：

- `nil`：该窗口无限额。
- `0`：完全禁用；因 usage 从 0 开始，任何请求都会达到上限。
- 正数：以 USD 计价的上限，预检查在 `usage >= limit` 时拒绝。

缺失行等价于该平台无限额。注册快照和新建管理配置只为至少一档非 `nil` 的限额建行，`0` 仍须建行；三档全空不会制造新记录。既有无限额行保留历史用量及窗口，重新配置限额不会凭空清除已经产生的统计。

日/周窗口使用站点全局时区的日首和周首；月窗口是从持久化起点开始的滚动 `30 * 24h`，不是自然月。窗口过期时预检查将本次判断中的 usage 视为 0；实际持久化窗口在后续成功结算时重置。预检查不清零数据库，也不刷新 Redis 快照。

## 请求准入

用户平台额度只在 `standard` 的余额结算路径生效；仍由有效订阅承接的请求豁免。订阅额度耗尽并回退余额后，重新进入平台额度检查。API Key 限速和用户/分组 RPM 继续独立生效。

所有平台统一以 PostgreSQL 为准，包括独立 Video。`BillingCacheService.checkUserPlatformQuotaEligibility` 只用 singleflight 合并当前同时在途的相同用户/平台查询，不缓存已完成的查询结果；下一次请求重新查数据库。`HasUserPlatformQuotaLimit` 同样读取数据库，旧 Redis 无限额占位、过期用量和失效失败不能遮蔽管理员配置。

数据库查询采用独立的三秒超时，不随首个请求取消而取消共享查询。数据库失败或调用请求上下文取消时保留既有 fail-open 行为并记录 warning；Redis 不再作为平台额度的故障回退来源。资金结算中的额度写入失败会回滚事务，不适用准入阶段的 fail-open。

批量图片和创作台在创建任务的资金预占事务内完成订阅分配后，仅对确实需要冻结余额的任务检查原平台额度。纯订阅和免费任务豁免；额度耗尽或数据库检查失败时，订阅分配、余额冻结、任务资金快照及请求去重一起回滚。检查仍使用当前有效用量 `usage >= limit`，不把本次预计消费提前累计，也不因为预计金额将超过限额而拒绝。完成捕获只记实际消费，不能因后来额度耗尽拒绝已受理任务。

额度耗尽返回 HTTP 429 和日/周/月专用错误码，并附 `window_resets_at`。客户端 `Retry-After` 从相同窗口口径计算，不能使用服务器 UTC 日界替代配置时区。

## 结算与持久化

非 Video 平台的额度计数通过 `applyUsageBillingPlatformQuota` 与真实资金扣款、请求去重在同一 PostgreSQL 事务提交。仅累计实际余额承担的金额，纯订阅金额、冻结额以及未发生资金扣款的重复命令不增加用量。平台归属优先使用请求冻结的 `QuotaPlatform`；兼容旧持久命令时仅从原任务或原分组恢复，不改读可能已换组的当前 Key。

批量图片和创作台捕获的平台金额按钱包同样的八位小数量化；价格计算的更细精度及原请求指纹保持不变，未实际扣除的小数尾差不累计进平台额度。

事务内锁定既有活跃额度行，确认至少配置一档 limit 后再累加三个窗口；缺失、软删除或三档全空的行不新建统计。取得行锁之后读取数据库时钟，避免排队跨日的旧时间把新窗口回退。实际金额、三个窗口和资金要么一起提交，要么一起回滚。进程在资金事务提交后退出，不需要再次执行平台额度副作用；资金命令的持久去重同时阻止重复累计。

独立 Video 继续使用任务预留、捕获和释放事务维护平台额度：预留冻结、成功捕获、失败释放使用原任务证据，通用资金路径跳过 `video`，不会二次累加。Video 的预留量可出现在额度占用中；其他平台仍在真实结算时累计，不因本次一致性修改变成通用预付费。

旧 `IncrementUserPlatformQuotaUsage`、`UserPlatformQuotaUsageFlusher` 和 `BatchSnapshotUsage` 保留调用接口但不再写平台用量。Flusher 的定时回调、直接调用和停止时的最后刷写全部停用；即使历史配置仍开启，也不能恢复绝对快照覆盖。旧缓存 TTL、sentinel TTL 和 flusher 配置仅兼容读取，不控制当前平台准入或统计。遗留 dirty set 不包含请求账本、资金分摊或管理员重置代次，不能自动合并进数据库。

## 默认值与管理操作

注册时把全局默认和认证来源默认合并为用户快照；后续修改站点默认值不追溯覆盖已有用户。快照写入只包括已配置限额的平台，并保留脱离注册事务、失败不阻断注册的边界。管理员读取、全量替换一个用户的十五个平台配置，或显式重置某个平台的指定窗口。管理员页面与请求准入均读数据库；现存 Redis 失效操作失败不再影响新限额和重置结果。迁移只扩展数据库平台约束，不为已有用户回填 CN 或 Video 行，也不清理历史无限额用量。

管理更新不能用缺失字段表达 `0`：JSON `null` 是无限额，显式数值 `0` 是禁用。全量替换需要审计新增、修改和移除的平台，避免未提交的平台静默保留旧限制。

全量替换中省略某个平台，或把该平台三档限额清空，都会取消对应限制，但保留既有行的 usage/window；重新设置限额沿用保留的窗口用量，窗口自然过期仍按原规则重置。管理员限额弹窗只允许重置服务端已经保存的行：只在输入框填写但尚未保存的新平台不可重置；既有无限额历史行仍可由管理员显式重置。

迁移 `291_video_quota_reset_generations.sql` 为三个窗口分别增加内部手动重置代次。管理员重置在清零用量、设置原有时间锚点的同一条 SQL 中推进所选窗口代次；自然过期刷新及限额编辑不推进。Video 预留保存代次，退款须同时匹配原行、窗口和代次，因此管理员同日/同周重置后，即使新请求将起点归一化回原日首/周首，也不会被旧任务退款扣减。普通平台结算与管理员修改通过数据库行锁串行，不再受旧 Redis 绝对快照覆盖。

## 一致性与升级

- 多实例共同读取、更新 PostgreSQL，实例内只合并同时在途的准入查询。已开始查询可能与并发重置交错，后续查询不保留旧结果；限额修改无需等待 Redis TTL。
- 余额请求的额度检查仍是请求前检查，已受理的并发请求可在完成时超过限额。数据库权威保证已结算用量不因崩溃丢失或重放翻倍，不等同于为所有平台实现原子额度预留。
- 升级必须完整停止或排空旧版本实例及其平台统计后台任务后切换。旧二进制仍可执行异步增量或绝对快照写回，不能保证新旧版本混跑的正确性。
- 切换前核对历史数据库统计基线。新实现不自动猜测历史漏记，不把 Redis 的最大值、dirty set 或绝对快照当作准确账本；需要回填时应根据可核对的已结算请求、真实余额分摊和窗口/重置记录单独处理。当前幂等保证针对新资金事务，不能推断旧版本提交时是否已经累计。
- 用户平台额度与账号上游 quota、订阅窗口、团队成员限额、Key 5h/1d/7d 限额分别排查，不能只看一个 “quota exhausted”。
