# 用户平台额度

本文描述用户在十一个平台上的日、周、月 USD 额度，从注册默认值、请求预检查、成功结算到 Redis/数据库同步的完整语义。它不描述上游账号套餐额度、订阅计划窗口或 API Key 自身限速。

## 额度模型

每个用户和平台最多一条 `user_platform_quotas` 活跃记录。允许的平台为 Anthropic、OpenAI、Gemini、Antigravity、Grok、Qoder、Kimi、Zhipu、DeepSeek、MiniMax 和 OpenCode。每条记录分别保存日/周/月 limit、usage 和 window start。国产供应商的 payg/coding 只是上游账号模式，用户额度仍按各自平台归属，不拆成额外平台。OpenCode 的 Zen/GO 同样共用 `opencode_go` 额度；迁移 277 只扩展允许的平台，不写入无限额记录。

limit 的三态语义是领域不变量：

- `nil`：该窗口无限额。
- `0`：完全禁用；因 usage 从 0 开始，任何请求都会达到上限。
- 正数：以 USD 计价的上限，预检查在 `usage >= limit` 时拒绝。

缺失行等价于该平台无限额。注册快照和新建管理配置只为至少一档非 `nil` 的限额建行，`0` 仍须建行；三档全空不会制造新记录。既有无限额行可以保留历史用量及窗口，也继续作为 Redis 待刷快照的目标。系统不会仅凭数据库当前 usage 为零自动清理这些行，因为异步模式下 Redis 可能已有尚未落库的用量。

日/周窗口使用站点全局时区的日首和周首；月窗口是从持久化起点开始的滚动 `30 * 24h`，不是自然月。窗口过期时预检查先把本次判断中的 usage 视为 0，月窗口起点按当前时间重置，随后刷新缓存或由数据库累加路径自愈。

## 请求准入

用户平台额度只在 `standard` 的余额结算路径生效；仍由有效订阅承接的请求豁免。订阅额度耗尽并回退余额后，重新进入平台额度检查。API Key 限速和用户/分组 RPM 在其后继续独立生效。

检查采用 Redis-first：当前 schema 的缓存命中直接判断；MISS 或旧缓存用 singleflight 合并数据库回源并回填。Redis 故障时仍查询数据库做一次性检查；数据库也失败或请求上下文取消时当前实现 fail-open 并记录 warning，避免额度基础设施故障阻断全部网关流量。

额度耗尽返回 HTTP 429 和日/周/月专用错误码，并附 `window_resets_at`。客户端 `Retry-After` 从相同窗口口径计算，不能使用服务器 UTC 日界替代配置时区。

## 结算与刷写

只有请求成功结算、平台在 allowlist、用户存在且该平台至少配置一个 limit 时才累加。累加金额是本次实际由余额承担的 USD 金额；纯订阅金额不计入。请求模型、上游模型和账号上游套餐都不能改变 `QuotaPlatform` 的平台归属。

Redis 用 Lua 同步累加三个窗口并标记脏 key，使下一次预检查立即看到新 usage，把并发超额范围限制在 in-flight 请求内。数据库有两种持久化模式：

- Flusher 关闭：成功结算后异步调用 `IncrementUsageWithReset`，数据库对既有行原子重置过期窗口并累加，缺失行直接跳过、不重新建行。正常无限额请求由结算守卫跳过；已经通过守卫的在途用量仍会写入原行，即使管理员刚取消其全部限额。
- Flusher 开启：Redis 为执法热状态，dirty set 由 `UserPlatformQuotaUsageFlusher` 分批读取绝对快照，通过 `UPDATE ... FROM` 更新既有活跃行。缺失或软删除行跳过，不通过异步快照重新创建配置。

Flusher 每批 Pop dirty key、批量读取 Redis、写入绝对 usage/window snapshot。普通写失败会把 key 加回 dirty set；当前仓储不再插入快照行，因此同批缺失用户不会引发插入外键错误、阻止其他既有行更新。兼容适配器的旧外键错误计数保留。已读取到的历史无限额快照仍会写入其既有行，避免清空限额时丢弃最后一批已产生用量。停止服务时会尝试最后一次 flush。Flusher 是异步镜像优化，不改变 Redis 预检查和成功结算的先后关系。

## 默认值与管理操作

注册时把全局默认和认证来源默认合并为用户快照；后续修改站点默认值不追溯覆盖已有用户。快照写入只包括已配置限额的平台，并保留脱离注册事务、失败不阻断注册的边界。管理员读取、全量替换一个用户的十一个平台配置，或显式重置某个平台的指定窗口。更新与重置后要失效所有相关 Redis entry；失效失败意味着新 limit/reset 最长可能延迟到缓存 TTL，应产生告警。迁移只扩展数据库平台约束，不为已有用户回填 CN 行，也不清理历史无限额用量。

管理更新不能用缺失字段表达 `0`：JSON `null` 是无限额，显式数值 `0` 是禁用。全量替换需要审计新增、修改和移除的平台，避免未提交的平台静默保留旧限制。

全量替换中省略某个平台，或把该平台三档限额清空，都会取消对应限制，但保留既有行的 usage/window；重新设置限额沿用保留的窗口用量，窗口自然过期仍按原规则重置。管理员限额弹窗只允许重置服务端已经保存的行：只在输入框填写但尚未保存的新平台不可重置；既有无限额历史行仍可由管理员显式重置。此策略不采用删除全部无限额行、清空限额即抛弃用量的行为。

## 一致性与诊断

- Redis usage 是当前执法视图，数据库 usage 在异步模式下可能滞后；管理端展示要注明读取来源或刷新状态。
- Flusher 写绝对值而非 delta，重试不会重复累加；dirty key 丢失可由后续活跃请求重新标记，但低活跃用户的数据库镜像可能长期偏低。
- 管理重置与正在执行的 flusher 存在已记录竞态；强制重置未过期窗口时应检查随后的 Redis/DB 值。仅更新既有行和保留历史行并未引入版本校验，也没有解决管理员清缓存与尚未读取的脏缓存之间的既有时序边界。
- 用户平台额度与账号上游 quota、订阅窗口、团队成员限额、Key 5h/1d/7d 限额分别排查，不能只看一个 “quota exhausted”。
