# 支付与权益

本文描述余额、订阅、兑换码和支付订单如何产生并撤销可消费权益。它用于修改支付或授权发放时保持金额、状态机和幂等不变量，不替代支付提供商接入参数、运营配置步骤或面向外部系统的接口手册。

## 权益模型

| 概念 | 作用 | 权威状态 |
| --- | --- | --- |
| 用户余额 | 没有适用订阅或订阅不足时承担网关消费 | 用户余额及其冻结金额，必须通过领域仓储原子调整 |
| `SubscriptionPlan` | 可售或可人工发放的权益模板 | 价格、币种、有效期、日/周/月额度、覆盖分组和分组倍率 |
| `UserSubscription` | 某用户实际拥有的带时间窗口权益 | 起止时间、active/pending/revoked 状态、额度快照、使用量和可选来源订单 |
| `RedeemCode` | 一次或有限次数的权益发放凭据 | 类型、值/套餐、有效期、最大次数、状态及用户兑换记录 |
| `PaymentOrder` | 外部资金事件与内部权益发放的协调记录 | 金额、币种/费用、订单类型、提供商与商品快照、状态、时间点和退款字段 |

订阅计划是可变商品配置，用户订阅才是已发放权益。购买订单保存计划快照，履约使用下单时的价格/权益语义，不能因管理员后来修改或删除套餐而改变已付款订单。余额订单与订阅订单共享支付确认流程，但进入不同履约分支。

每日活动的充值资格同时支持在线余额充值本金及外部订阅实付金额；订阅取原订单 `pay_amount` 数值，不换汇，排除站内余额支付。首次开启后曾履约成功且有 `completed_at` 的订单，退款申请、处理中、失败、部分退款或全额退款均保留原活动累计金额和领取资格；每日礼包仍归属原完成日，未完成订单不计入。活动不改变原支付、订阅发放或退款金额，具体规则见[每日活动](daily_activities.md#daily_activity_eligibility)。

## 订单与快照

创建订单前应完成用户归属、支付功能开关、订单类型、提供商实例、支付方式、币种、金额范围、套餐在售状态和促销规则校验。`out_trade_no` 是发给外部提供商的唯一商户订单号；本地数值 ID 只用于内部查找，旧版编号格式仅保留兼容回退。

订单类型仅允许精确的 `balance` 与 `subscription`；创建请求省略类型时默认 `balance`，大写、空格或其他值一律拒绝。HTTP 绑定、服务创建、报价和履约分别维护此边界；历史异常订单不能被默认当成余额发放，直接调用余额或订阅履约入口也必须匹配订单类型。

订单持久化以下创建时事实：

- 应发权益金额 `amount`、实际支付金额 `pay_amount`、费用比例/固定费用及币种口径。
- `order_type`，以及订阅订单的 `plan_id` 与 `plan_snapshot`。
- `provider_instance_id`、`provider_key` 和 `provider_snapshot`，使回调、查单与退款仍使用原订单对应实例。
- 客户端来源、过期时间、外部 trade number、invoice/receipt 信息及完整状态时间点。

提供商实例决定支持的支付类型、模式、限额、排序和退款能力。删除或修改当前实例不能把历史订单重新解释为另一个实例；解析旧订单时才允许按保存的 provider key 或兼容注册表回退。

EasyPay 自定义支付方式区分本地 `type` 和上游 `upstreamType`：前者仍限制为小写字母、数字、下划线和短横线，后者额外允许点号以兼容如 `usdt.trc20` 的上游标识，其他非法字符继续拒绝。该放宽不修改站内余额支付或历史订单类型。

## 充值优惠阶梯

余额充值可配置最多 20 个金额档位，按用户原始输入金额命中不超过该金额的最大阈值。赠金模式在 `输入金额 × 充值倍率` 的到账基数上增加赠送；折扣模式保留该到账基数，按档位百分比降低网关收款基数。阈值和百分比最多两位小数，折扣必须小于 100%；未配置或未命中保持原有报价。订阅外部支付及站内余额购买订阅不参与活动。

统一顺序为原始金额和币种精度校验、阶梯报价、现有固定手续费及比例手续费、渠道实付限额校验。折扣后的金额不能用来掩盖原始输入的非法精度；到账金额超出余额列精度时拒绝下单。前端预览沿用站内余额单位，支付金额使用具体支付方式的币种；公告 Markdown 必须清洗后展示。

阶梯阈值按所选支付方式币种下的原始输入金额匹配，不先换汇。后台完整但非法或重复的档位阻止整次保存，空白草稿可忽略。外部订阅的方式列表、按钮及提交保护统一按换汇和手续费后的实付校验渠道限额；钱包购买仍按套餐原价扣除余额，不参与充值活动。

优惠模式与档位属于同一个配置约束。后台 PATCH 在数据库事务中按固定顺序锁定这两个设置键，读取现值、合并缺省字段、校验后保存整次请求；初次缺省键也在同一事务建立。多个服务实例并发更新时，后到请求依据已提交值重新校验，非法组合返回错误且其他同批配置一并回滚。

前端报价按十进制输入逐步运算，分别对到账基数、赠金、折后支付基数和已付金额对应额度舍入，避免浮点半分边界与后端 Decimal 相差一分。快捷金额的折后提示不含手续费，最终实付在渠道费用汇总中展示。

输入金额及派生报价出现非有限值或溢出时，前端不得展示为合法报价或继续提交；不能通过把异常金额归零绕过渠道限额。服务端继续独立校验原始金额、币种精度和到账余额范围。

订单 `amount` 保存含优惠的到账总额，`bonus_amount` 保存其中免费获得的额度，`pay_amount` 保存渠道最终实收。优惠在创建订单时固化，后续更改活动不重算旧订单；履约只发放一次 `amount`，不得再次累加 `bonus_amount`。本站返利仍按既有到账积分与套餐快照口径计算，退款继续按退款额度占原到账总额的比例换算原实付；不采用上游剔除赠送额后的返利规则。

订单金额、实付、手续费、赠金与退款快照统一使用 `decimal(21,3)`，保留原有整数容量，支持 KWD 等三位小数币种。余额到账与赠金仍按原业务规则舍入两位；币种最小单位和验款容差保持不变。渠道退款提交与异步查询均按原实付比例换算，按订单币种格式化金额，不能把权益退款额直接当作渠道退款额。

## 支付状态机

正常成功路径为：

```text
PENDING -> PROCESSING -> PAID -> RECHARGING -> COMPLETED
    |          |            |          |
    |          +----------> EXPIRED    +-> FAILED -> retry
    +-> CANCELLED / EXPIRED
```

- `PENDING` 表示已创建且仍可由用户/管理员取消；外部报告处理中时用条件更新进入 `PROCESSING`。
- 支付成功先核对有限正数金额和币种最小单位容差，再从 `PENDING`、`PROCESSING`、`EXPIRED` 或 `CANCELLED` 恢复到 `PAID`。晚到成功不能因为本地超时而丢失真实付款。
- 履约通过条件更新获取有时限的 `RECHARGING` lease；只有 lease 持有者可以发放权益并进入 `COMPLETED`。
- 履约错误进入 `FAILED`，管理员或后台对账可以重试；卡住超过 lease 时限的 `RECHARGING` 也可被安全接管。
- 订单类型只允许 `balance` 与 `subscription`。历史异常类型的已付款订单收敛为 `FAILED` 并审计，回调正常确认但不发放权益；管理员重试返回 `INVALID_ORDER_TYPE`。数据库写入失败仍返回错误，不能提前确认回调。
- 提供商明确失败可把尚未付款的 `PENDING/PROCESSING` 订单记为 `EXPIRED`。未知或不支持的回调状态不应猜测成功。

取消和过期不是简单的本地状态写入：订单已经关联外部支付时要先查单；如果提供商显示已付款或仍在处理，则不能把它覆盖成未付款终态。调用上游取消失败后需要再次查单，处理付款与关闭并发。所有状态迁移使用旧状态条件更新，竞争失败后重新读取当前状态并按实际终态返回。

### EasyPay 查单兼容

EasyPay 实例使用 Z-Pay 官方域名 `zpayz.cn` 或 `www.zpayz.cn` 时，依据 [Z-Pay 接入文档](https://zpayz.cn/doc.html)直接以 GET 请求 `/api.php`，在查询参数中传入 `act=order`、`pid`、`key` 和 `out_trade_no`。只精确匹配解析后的主机名，不把相似域名、路径或查询字符串中的域名文本当作 Z-Pay。官方 GET 返回失败或空响应时不再尝试 POST；创建支付和退款保持各自原有方法。

其他 EasyPay 实例保留先向 `/api.php` 发送表单 POST 的兼容行为，同时将相同参数放在 URL 查询中，兼容只读取查询参数的 PHP 实现。仅当返回 HTTP 2xx 且正文为空或全为空白时，以相同参数单次回退到 GET；POST 的 HTTP 错误、业务失败 JSON、HTML 或传输失败不触发此回退。单次查单的 POST 与 GET 共享总超时预算，两种方法都禁止重定向；查询 URL 中的商户凭据和原始错误正文不得进入日志、审计或客户端错误。

查单必须取得明确的成功业务码 `code=1` 和已知支付状态。状态字段按顶层 `trade_status`、嵌套 `data.trade_status`、顶层 `status`、嵌套 `data.status` 的顺序选择首个非 `null` 字段：`TRADE_SUCCESS` 或数值 `1` 表示已付，`WAITING`、`WAIT_BUYER_PAY` 或数值 `0` 表示未付。选中的状态为空字符串或未知值时不能降级读取低优先级字段；缺失状态、失败业务码和非 JSON 等无效响应均不能当作未付。

`code`、`status`、`money`、`trade_no` 兼容 PHP 返回的数字与数字字符串，但业务码和状态仍要求明确合法值，不能接受小数业务码、布尔值或对象。返回顶层或 `data.out_trade_no` 时必须匹配本次查询的商户订单号；缺失渠道交易号时普通查单仍保留旧兼容回退，回调主动确认不把这个回退值当成真实渠道交易号。

EasyPay 当前没有上游关单实现，确认未付后沿用现有流程写入本地 `CANCELLED` 或 `EXPIRED`，迟到付款仍可恢复履约。已付结果仍核对金额并进入幂等履约，不能被取消覆盖。GET 后仍无法确认时，普通取消或超时关闭继续保留 `PENDING` 并遵守下述失败退避规则，不因此自动强制过期。

后台支付配置的连通性测试使用随机订单号，不创建真实订单。明确的“订单不存在”业务响应以脱敏错误 `ErrEasyPayOrderNotFound` 返回；只有此随机探测将其视为接口可达。真实订单的查询、取消和过期仍将该错误视为无法确认状态；其他业务错误、鉴权失败和无效响应也不能作为配置测试成功。

<a id="forced_expiration_recovery"></a>
### 强制过期与失败退避

普通用户取消、管理员普通取消和后台超时关闭都保持 fail-closed：无法查询上游状态时，接口返回 `PAYMENT_STATUS_UNAVAILABLE`，订单继续为 `PENDING`，不能把可能已付款的订单直接关闭。失败首次写入 `PAYMENT_CANCEL_FAILED` 审计，并刷新订单 `updated_at`；超时 worker 仅在上次失败超过 15 分钟后重试，避免错误地址或暂时故障导致每分钟重复查单。

管理员可针对单笔 `PENDING` 订单调用强制过期操作，提交 1 至 500 个字符的原因。该操作不访问上游，在同一事务内使用条件更新写入 `EXPIRED` 并记录 `ORDER_FORCE_EXPIRED` 审计；审计写入或提交失败时必须整体回滚，状态已变化时返回冲突。它是明确的人工恢复手段，不替代普通取消或自动过期策略。有效的迟到付款通知仍可从 `EXPIRED` 进入 `PAID` 并按既有幂等履约流程处理。

存在仍为 `EXPIRED` 的 `ORDER_FORCE_EXPIRED` 订单时，原 provider instance 可以禁用，但不能硬删除。回调验证和迟到付款恢复仍需要该实例的历史凭据；订单恢复到非过期状态后，这项强制保留约束自动解除。

## 回调安全

Webhook 路由不依赖用户 JWT，因此提供商验签、订单绑定和金额验证构成授权边界：

1. 限制请求体大小，按提供商读取原始 body/query 和必要 header，不能先做会改变签名输入的重新序列化。
2. 尽可能从商户订单号找到原订单的具体 provider instance；多实例无法预判时逐个候选验签，只有成功验签的实例可以解释通知。
3. 验证 provider 自身签名、时间戳/重放窗口和事件类型，再验证通知中的 provider、trade number、订单 metadata 与本地快照一致。
4. 核对通知金额为有限正数且与订单 `pay_amount` 在币种容差内一致，之后才允许进入 `PAID`。
5. 不相关事件返回提供商要求的成功响应；验签或处理失败返回失败以便重试。确实不存在的本地订单可确认接收以阻止无意义重试，但必须留下告警。

EasyPay 回调字段仅允许真实通知参数，含 `return_url`、`notify_url` 等下单专属字段、未知字段或重复字段时拒绝。`pid` 必须等于验签实例的商户号；除自由文本 `name` 外，字段值禁止 `&` 与 `=` 分隔符。验签成功的支付通知还须由**同一实例**主动查单，核对已付状态、有限正数金额及存在时的渠道交易号；通知缺失交易号时可以从查单补充。失败写入 `PAYMENT_UPSTREAM_UNCONFIRMED` 审计并返回 HTTP 502 供渠道重试，不进入履约，后台对账恢复仍可用。其他未实现 `NotificationConfirmer` 的支付渠道保持原流程。

客户端结果页 URL 的查询参数与片段会被清除，再由服务器添加受控参数；禁止 userinfo 与非普通主机名，允许普通域名及 IPv4/IPv6、端口。Stripe 跳转不再把 `client_secret` 放在 URL，支付页只读取与当前订单和恢复令牌匹配、尚未过期的本地恢复快照；URL 中自带的密钥不能作为后备来源。真实订单仍可通过查单恢复；Z-Pay 的 GET 查单兼容保持不变。

匿名旧订单号验证入口按 IP 限制每分钟 20 次；它不是认证边界，Redis 故障时沿用支付可用性策略放行，结果查询本身的订单凭据校验仍执行。已登录查询、支付回调和后台对账不共用此限流桶。

回调是主要信号，主动 verify/查单和后台 reconcile 是漏回调、弹窗支付或进程中断后的恢复路径。它们必须复用同一状态迁移和履约函数，不能另写一套直接加余额逻辑。

## 履约与幂等

余额订单通过订单专属 `recharge_code` 复用兑换领域的原子权益调整：代码不存在时创建，存在但未使用时继续兑换，已经使用时只补齐后续步骤。订单级返利有自己的审计去重，兑换层在该路径跳过重复返利。只有权益与适用返利完成后，持有 lease 的调用者才能条件更新到 `COMPLETED`。

订阅订单调用 `AssignOrExtendSubscription`，把 `source_order_id` 设为订单 ID。服务在事务中锁定用户行后再次查询来源订单和最新同套餐订阅，使同一用户的并发发放先串行再扩展时间链；已有来源订单订阅则直接复用，因此 webhook、查单、人工 retry 和后台 reconcile 不会为同一订单重复发放。当前同套餐尚未过期时，新订阅从上一份 `expires_at` 开始并进入 `pending`，而不是覆盖或并行消耗。

支付审计日志记录下单后的重要动作、operator 和详情。通知邮件等副作用在完成后异步派发，失败不能回滚已发权益；需要凭订单完成状态和审计动作避免重复通知。

## 站内余额购买订阅

站内余额仅用于购买和续费订阅，不用于给同一余额账户充值。管理员在“系统设置 - 支付设置”开启站内余额支付；数据库键 `wallet_payment_enabled` 默认关闭，与外部充值入口的 `balance_disabled` 独立，新购仍要求支付总开关开启。购买和续费共用 `/purchase` 的订阅确认流程，关闭开关后前端隐藏余额选项，服务端同时拒绝新的余额交易。

下单复用 `POST /api/v1/payment/orders`，请求为 `payment_type=balance`、`order_type=subscription` 和 `plan_id`，并携带必填 `Idempotency-Key` 请求头（1 至 128 个可见 ASCII 字符）。价格以事务内读取的在售套餐 `price` 为准，按 USD 站内余额原价扣除，不采用充值倍率、外部渠道手续费或订阅 CNY 换算汇率；客户端传入的 `amount` 不决定扣款额。冻结余额不参与购买，也不允许购买形成负余额。

同一事务内锁定付款用户，使用“用户 ID + 幂等键”的摘要生成唯一商户订单号，检查已完成交易、复核余额、扣款、创建订单、复用订阅发放及同套餐排队逻辑，并写扣款与订阅审计。事务全部提交后才返回 `COMPLETED`，任一步失败则余额、订单、订阅与审计全部回滚；网络中断后同用户、同幂等键、同套餐的重试返回原订单，不重新扣款。将同一键用于不同套餐返回 `IDEMPOTENCY_CONFLICT`。已完成交易的恢复不受后来关闭支付开关或下架套餐影响。

新余额订单号采用 `bal_` 加 128 位摘要的无填充 Base64URL 编码，共 26 个字符；完整 SHA-256 摘要保存在提供商快照的 `wallet_request_hash` 中，命中短编号后仍校验完整摘要。历史 60 字符编号保留原值，幂等重试同时查找新旧格式，不因编号缩短重新扣款，也不修改历史查单链接。

前端在付款成功前保留本次确认的幂等键，网络失败及页面刷新后重试沿用；成功或另选套餐开始新一笔确认时更换。余额不足返回 `INSUFFICIENT_BALANCE`，新交易被开关禁止返回 `WALLET_PAYMENT_DISABLED`；接口之外的前端余额检查仅用于提示，不能代替事务内校验。

余额支付成功后刷新资金及认证缓存，并使用既有订阅通知；内部资金消费不重复触发充值返利。订单列表、审计和支付概览保留该交易，概览金额表达订单支付交易量，不能将充值和后续余额消费的合计解释为新增外部收款。本地余额交易没有第三方支付实例、二维码或网关发票，不走外部支付退款；原有订阅撤销也不会自动退回余额。

## 支付概览统计

管理员订单管理的支付方式支持 `balance`（站内余额），可与 `order_type=subscription` 组合筛选购买和续费订单；订单类型 `balance` 仍表示余额充值，不能与同名支付方式混淆。筛选选项不依赖当前支付开关，关闭余额支付后仍能查看历史交易。

支付概览按 `paid_at` 的起始时间包含、结束时间不包含范围统计 `PAID`、`RECHARGING`、`COMPLETED` 订单。站内余额购买和续费计入范围内支付金额、订单数、平均金额、每日趋势、支付方式分布、套餐购买分布和消费排行。今日卡片始终按当前自然日独立查询，不随历史日期范围变化；取消、未支付、失败、过期和退款状态不进入这些已支付统计，沿用现有状态口径。

统计 API 的金额卡、每日趋势、支付方式和消费排行按订单保存的币种分别聚合；购买分布同样按套餐与币种聚合，返回逐项 `currency`，禁止直接相加 USD 余额消费与 CNY 外部订单。管理端支付概览只隐藏 USD 金额投影：金额卡、金额趋势、支付方式金额和消费金额排行不展示美元，保留其他币种及全部订单数量；购买分布选择 USD 时保留购买项、订单数占比和数量明细，隐藏金额占比与金额列。此过滤不修改原始 API 响应、历史订单或后台统计，也不把美元折算或合并为人民币。

界面使用“支付金额”并说明包含余额支付，统计的是订单交易量，而非净新增资金。平均余额单位购买单价仍只使用原有外部订单样本，排除站内余额消费，避免将已经购入的余额重复计入购入成本与数量。统计直接查询历史订单，修正口径无需迁移或回填。

## 退款

退款只从允许的已完成余额订单及配置为可退款的 provider instance 发起，用户自助退款还要满足实例 `allow_user_refund` 和业务资格。退款状态族包括 `REFUND_REQUESTED`、`REFUNDING`、`REFUND_PENDING`、`PARTIALLY_REFUNDED`、`REFUNDED` 和 `REFUND_FAILED`。

调用提供商退款前后都使用条件状态迁移和查单恢复。Stripe 退款使用订单号与最小货币单位退款额组成稳定幂等键，同金额重试不得创建第二笔渠道退款，不同金额则保持独立。提供商返回 pending 时保留已执行的扣减，并在同一事务中记录 `REFUND_PENDING` 状态与 `deductionHeld` 快照，不能提前退回余额，也不能对 pending 订单再次发起退款。渠道确认成功时不重复扣减；明确失败时，条件认领、归还权益与失败审计同事务提交。归还失败则将失败状态和 `REFUND_ROLLBACK_FAILED` 一并落库，该订单须人工核查，准备及执行退款返回 `REFUND_MANUAL_REVIEW_REQUIRED`，不能跳过扣减后再次提交。协议异常、空响应或未知状态只报查询错误并保持 pending，不能推断退款失败。扣减和归还后失效余额准入缓存。

历史 pending 审计没有 `deductionHeld` 时，继续按原 `deductBalance`、实际扣减额和 `deductionRollbackOK` 快照收敛，保留管理员“不扣权益”选择；渠道退款查询沿用原实付比例和币种精度，不能把权益额度直接作为退款金额。审计读取或 JSON 解析失败必须停止收敛，不能当作旧记录再扣一次。退款不修改原 `completed_at`，也不减少每日活动累计或领取资格。

支付宝新增退款保存真实 `out_request_no`，查询通过 `alipay.trade.fastpay.refund.query` 追踪该次请求；`REFUND_SUCCESS` 表示成功。成功响应中查无退款记录时，自本地 pending 审计创建时间起至少等待 10 分钟才允许判失败；时间未知的历史记录继续待确认，业务失败、传输失败与空响应均不能当作查无记录。旧版本保存交易号而非退款请求号的订单返回 `REFUND_QUERY_UNSUPPORTED`，需要人工核实。

余额退款在非强制模式下发现余额不足时返回 `require_force`，只有管理员明确确认后才允许继续；执行时通过原子足额扣款再次确认余额，准备之后的并发消费不能使普通退款悄悄变为少扣权益的强制退款。强制退款只能原子扣除当时可用的非负余额，并将实际扣减额写入结果和审计。归还余额使用纯余额增量，不增加历史充值总额。订阅相关退款需要识别由 `source_order_id` 发放的订阅及其 active/pending 状态。强制退款属于明确的管理员操作，必须审计其理由，不能成为普通错误恢复路径。首次尝试返回 `require_force` 时，管理端保持退款弹窗、展示服务端警告，并且只有管理员显式勾选强制确认后才能携带 `force` 重试；关闭或重新打开弹窗必须清除上一次确认状态。

扣减会耗尽整份订阅时，先暂设 `suspended` 并保存本订单对应的原状态、有效期及版本，不提前软删除或推进套餐链。退款明确成功后，在订单终态事务内沿用原撤销及接续链逻辑；明确失败则恢复原状态，不增加天数、不清零用量。恢复只允许原用户、原 `source_order_id` 和未被其他操作修改的暂停版本；冲突保留人工核查审计，不能恢复别的退款或覆盖管理员变更。暂停及恢复均先锁行，按旧状态结清自然重置次数，再与新状态同一条更新写入；暂停段只推进统计水位，不累计自然重置次数。正常部分有效期扣减仍沿用订阅服务；归还时若扣减后的订阅已经到期，则保留回滚失败审计并转人工核实，不能从当前时间重新续期而赠送等待渠道期间的额外权益。

订阅暂停与 `REFUND_SUBSCRIPTION_HELD` 快照在同一事务提交；暂停、恢复及最终撤销在提交后失效该用户的鉴权/API Key 快照。若进程在暂停后、保存渠道响应前中断，超过 15 分钟的 `REFUNDING` 订单可通过退款查询恢复为受理不明的 pending，但必须同时匹配本次订单认领时间之后的审计和当前订阅暂停版本。没有本次渠道退款号时返回 `REFUND_QUERY_UNSUPPORTED` 并由管理员核实，不自动重发退款，也不推断失败后归还权益。该恢复仅适用于已持久化暂停快照的订阅退款，不将其他历史 `REFUNDING` 订单视为可安全重试。

管理员订单列表为 `REFUNDING` 与 `REFUND_PENDING` 提供“查询退款状态”，处理中只允许查询，不能重新发起退款。15 分钟内的处理中订单返回等待提示；即使查询最终返回人工核查错误，前端也刷新列表，以展示后台已经恢复为 pending 的真实状态。

## 订阅生命周期

用户订阅复制发放时的有效期和日/周/月额度。状态语义为：当前开始时间已到的有效记录为 `active`，未来排队记录为 `pending`，人工撤销为 `revoked`；软删除也按 revoked 处理。是否可消费还要求当前时间落在 `[starts_at, expires_at)`、所有已配置的有限额度窗口均未耗尽，并满足套餐分组范围。

套餐分组为空表示该套餐不限制分组；非空时表示可消费的显式集合。用户的订阅列表响应以 `groups_restricted` 和带名称的 `applicable_groups` 展示这一区别。只有 API Key 显式选择该订阅时，才把 Key 的可选分组收窄到用户原有权限与该集合的交集；自动结算和仅余额 Key 不因用户持有受限套餐而被全局收窄。指定订阅的付款主体仍按 Key 归属解析，团队 Key 使用 Team Owner 的订阅权益。

“我的订阅”的可访问分组复用 `GroupBadge`，优先使用 `display_brand` 的品牌图标及配色；未设置展示品牌时，通过 `resolveProviderBrandKey` 将 `platform` 匹配到同一品牌配色，无法匹配时保留平台样式，同时兼容深色模式和长名称省略。标签逐项显示该套餐下的分组倍率，`applicable_groups[].rate_multiplier` 由后端按既有计费规则解析：计划为该组设置有效的额外倍率时直接覆盖默认值，没有有效覆盖时使用分组默认倍率，不与默认值相乘，也不使用用户专属倍率。分组默认 `0` 合法并显示为 `0x`；计划倍率仍按既有配置规则要求正数，历史无效的 `0` 不代表免费覆盖。分组无法加载且没有可核实的计划覆盖时省略倍率，保留原有名称或 ID 占位，不能在界面猜测为 `0x` 或 `1x`。不限分组的套餐继续显示全部可访问分组的说明，不额外枚举全站分组。

API 密钥创建和编辑在指定订阅后使用相同的分组倍率，普通分组、复合分组以及智能路由候选保持一致；切换订阅会按新订阅重新取得权限交集及倍率，切回自动或余额模式恢复原有分组/用户倍率展示。倍率投影只作用于接口返回副本，不修改分组配置、套餐配置或实际计费规则；请求的高峰及其他价格因子仍使用原有计算流程。

自动结算优先消耗下一次额度重置或到期时间最近的可用订阅，不只比较套餐有效期。预检、倍率解析和锁内分配共用[自动结算的订阅顺序](routing_and_billing.md#automatic_subscription_priority)；窗口时间使用下述既有规则，排序本身不推进持久窗口、不修改额度或历史结算。

<a id="subscription_quota_windows"></a>
### 周期额度窗口

周期额度与 [sub2api 的窗口算法](https://github.com/Wei-Shaw/sub2api/blob/7c0a2a556c440836c54b3f3135f033755f15ecb7/backend/internal/service/user_subscription.go)对齐。日额度按项目时区的日历日每天 0 点刷新；激活或手动重置写入当天 0 点，历史非零点日锚点在下一个 0 点自愈。周、月额度分别按 7×24 小时、30×24 小时推进：首次使用和管理员手动重置取实际操作时刻，自动刷新按原锚点的整数周期推进，延迟请求或停机不会将后续刷新时间改成请求时刻或当天零点。旧周/月锚点只有在恰好等于生效当天零点且早于生效时刻时才修正为 `starts_at`；后续零点可能来自手动重置，仍保持原值。

订阅有效期间首次使用可以激活配置了正数额度的空窗口，不要求剩余完整周期；补齐空锚点保留历史用量，只有已到期的旧窗口才清零。自动刷新仅要求下一次重置严格早于 `expires_at`，取消原先“下一窗口还须完整落在有效期内”和“有限外层额度保护”的限制。未配置、零值或负数额度仍表示无限；有效期不超过一个日历日的日额度仍是一次性额度，不因跨零点而刷新。管理员延长或调整有效期后仍在同一事务内维护窗口和后续排队订阅，立即返回可用的重置时间；这部分沿用 fork 的事务与套餐链规则。

实际扣费窗口仍在到点后的请求准入或维护中推进并持久化清零；后台计数任务不清零额度、不改变窗口锚点。无请求时数据库可能保留上一窗口的累计值，不等于下一次消费仍会使用过期额度。管理员和用户页面共用按项目时区计算的重置时间，下一重置点早于到期就显示刷新倒计时；等于或晚于到期、或者属于一次性日额度时显示结束倒计时。周/月进度接口与上游一样保留原始 `anchor + period` 候选值，由界面判断到期边界。例如周锚点 9 月 23 日、订阅 10 月 5 日到期，应显示 9 月 30 日刷新；无需再延长至 10 月 7 日。

“我的订阅”和管理员订阅列表在各有限额度窗口下展示 `daily_reset_count`、`weekly_reset_count`、`monthly_reset_count`。次数按本期已到达且符合额度规则的重置时间累计，不依赖是否发生消费；未使用、用量为零、从未激活实际窗口的订阅也会计数。首次激活及管理员手动重置本身不加次数；同一期的编辑、延期和恢复保留已累计值。续费仍创建下一期记录，新一期从零开始，尚未生效时不清空当前一期的计数。

订阅另有内部 `daily_reset_generation`、`weekly_reset_generation`、`monthly_reset_generation`，由迁移 `291_video_quota_reset_generations.sql` 加入，与展示的自然重置次数无关。单条及批量管理员重置在原行锁事务内推进所选窗口代次，保留原有时间、用量和次数语义；自然刷新、编辑、延期和恢复不推进。重置必须以同一条更新写入窗口、用量、次数水位及代次，避免同事务再次更新触发额外用户外键锁，与批量延期的用户锁形成等待。独立 Video 预占保存窗口起点及代次，退款同时核对二者，防止同日手动重置后旧任务减掉新用量；既有图片规则不变。

计数是 fork 保留的扩展，以上游窗口规则为时间表，以持久化 `reset_counted_at` 为排他的起点，统计到当前时刻（包含）且严格早于到期的重置点。已有实际窗口时采用与额度维护相同的锚点和旧初始零点修正规则；尚无窗口时，日额度以生效当天的项目时区零点为基准，周/月额度以精确 `starts_at` 为基准。有效尾段同样计数，不再检查剩余完整周期或外层额度；一次性日额度、无限额度、到期时刻以及暂停、撤销、软删除期间不计数。实际激活或手动重置改变锚点后，后续次数随新的时间表累计，既有次数保留。

现有订阅过期服务在启动时及每分钟扫描分批结算次数；数据库行锁、水位与次数原子更新支持多实例和停机后的多周期补记，跳过的繁忙记录由后续扫描补齐。过期记录可结清到期前符合条件的次数，结清后退出扫描。列表使用同一算法投影到查询时刻，用户无需调用大模型即可看到到点后的次数；该投影不改变实际扣费窗口。后台计数失败单独记录日志，不阻止原有订阅过期维护。

任何实际窗口、有效期、开始时间、额度或状态变更都先在同一行锁事务中按旧状态结清次数，再应用新状态；事务扣费也在归一化窗口前计算并与账务一起提交，回滚不会留下计数。管理员延期不会追补旧有效期结束后已过去的时点，但延长后到达的重置点继续计数。手动重置前已经到点的次数保留，避免页面展示后回退。切换规则不清零或猜测重算已有历史累计值，不改变额度上限、余额或扣费金额。

迁移 `285_subscription_scheduled_reset_counts.sql` 为既有记录以迁移时间建立水位并保留三个已有计数，不猜测升级之前的历史；新记录以创建时间建立水位，未来排队订阅仅在生效之后计数。新旧后端的计数语义不同，升级时须完整切换后端实例，不能混跑旧的“实际推进加一”与新的“到点按水位累计”。

事务结算仍把订阅承担的消费累计到所有已配置的有限窗口，各窗口独立刷新，尚未到期的其他窗口累计值仍是新请求的硬性准入上限。普通请求通过预检并成功完成后，如果最终费用跨过指定订阅的剩余额度，事务必须把订阅用量封顶在可用额度，并将未覆盖的基础用量按余额倍率扣入付款主体余额，余额不足时允许形成负数欠费；不能因严格封顶导致结算回滚和零计费。该欠费只用于结算已经放行或并发在途的请求，不赋予额外权益，后续绑定该订阅的新请求仍按 `used >= limit` 拒绝，不因余额可用而自动回退。批量任务在提交上游前的额度预占不适用该例外，指定订阅无法完整覆盖时必须回滚并拒绝。服务层预检、额度进度展示和数据库事务归一化共用窗口规则，不能让缓存判断与最终扣费出现分叉。结算在数据库事务中锁定并累计当前使用；读取缓存仅用于热路径预检，订阅创建、延长、重置、撤销、恢复、过期和使用量变化后必须失效 Billing/API Key 认证缓存。

同用户同套餐的连续订阅形成时间链。延长或调整有效期需要保持后续 pending 记录不重叠；恢复已撤销记录也要重新计算插入位置。`source_order_id` 是支付发放幂等键，人工发放、默认注册发放和兑换码发放没有来源订单时使用各自的事务/锁边界。

<a id="subscription_self_revoke"></a>
用户自助撤销只允许作用于本人当前 `active` 订阅，且只在最高层已配置的正数有限额度耗尽时开放：优先检查月额度，其次周额度，最后日额度；低层窗口暂时耗尽或套餐没有有限额度都不能撤销。`POST /api/v1/subscriptions/:id/revoke` 在同一事务中复核状态和额度、软删除当前记录并平移后续同套餐链；第一份 pending 因此立即生效。若存在接续记录，所有 `billing_mode=subscription` 且显式绑定旧订阅 ID 的个人、团队、复合和托管 API Key 一并改绑到接续记录；没有接续记录时保留旧绑定并使其不可用。该操作不退款，用户不能自行恢复。

<a id="subscription_admin_bulk"></a>
### 管理员批量操作

管理员订阅列表采用上游批量操作栏与可滚动确认清单，支持当前页选择 1 至 100 个订阅，分别进行延长、重置、撤销或恢复；翻页、排序、切换筛选时清空选择，不默认操作未显示的记录。延长与重置仍检查完整选择，仅接受 `active`、`pending`、`expired` 记录，拒绝已暂停或已撤销记录。撤销按钮筛选全部未撤销记录（包括待生效、已过期与暂停），恢复按钮只筛选已撤销记录，操作前清单明确展示最终目标；不同状态混选不会把已撤销记录再次撤销。

`POST /api/v1/admin/subscriptions/bulk-extend` 接收 `subscription_ids` 和正整数 `days`（最多 36500），`days` 表示在原到期时间上增加的天数；已过期的链末尾记录从当前时间起算。该含义与既有单条 `/:id/extend` 的“设置目标有效天数”保持区分，单条接口不变。已过期且同用户同套餐仍存在后继未撤销记录时，批量延长返回 `SUBSCRIPTION_BULK_EXPIRED_HAS_SUCCESSOR`，要求改选最后一份订阅；即使后继记录也已过期，仍拒绝恢复早期历史记录，避免顺延时重新激活未选中的历史权益。批量重置不应用该延长专属限制。

`POST /api/v1/admin/subscriptions/bulk-reset-quota` 接收 `subscription_ids` 和 `daily`、`weekly`、`monthly`，至少选择一项。服务复用原有 `AdminResetQuota` 的窗口锚点和用量清零规则，只改被选中的窗口，不改套餐、额度上限或到期时间。

`POST /api/v1/admin/subscriptions/bulk-revoke`、`bulk-restore` 接收 `subscription_ids`，复用单条撤销与恢复领域逻辑。撤销沿用同套餐后继前移；恢复保留原始有效期和已用额度，以软删除状态判定可恢复性，再按当前时间推导状态（原暂停记录仍遵循暂停规则），不强制激活或延期。恢复后与其他同套餐记录重叠时，返回冲突并回滚整批。

上述四个批量入口均需要管理员权限和 `Idempotency-Key`。服务先校验数量与 ID 并去重，在一个事务内按用户 ID 升序锁定用户，锁后复核资格，按用户、套餐、原开始时间、订阅 ID 的稳定顺序串行调用现有单条领域方法。同套餐的多个选中订阅各自增加一次时长，后继链按既有规则顺延；任何记录失败则整批回滚，响应的安全错误包含 `metadata.subscription_id` 供定位。成功返回 `{subscription_ids, updated_count}`，ID 保留去重后的请求顺序。该路径不发送邮件，不变更既有单条业务规则，也不引入新的缓存或异步任务。

页面在首次提交时固定参数和幂等键，使用按管理员 ID 隔离的 `sessionStorage` 保存最少的请求和确认清单，关闭弹窗、切换页面或刷新浏览器后可以继续确认原请求；列表中原行消失也保留独立恢复入口。成功后清理待确认操作并刷新列表，首次明确未执行或整批回滚的业务错误允许改选；已经发生未知结果后，不用后续失败推断此前没有执行。接口错误按 `apiClient` 归一化的顶层字段读取。接口复用现有管理员幂等协调器，幂等存储故障采用 fail-close；业务事务与协调器成功记录并非一个数据库原子提交，原有延长、重置等入口的进程故障窗口仍按原协调器的 processing/冲突恢复规则处理，不承诺跨故障的严格 exactly-once。

分配弹窗保留单用户入口，并增加最多 100 位现存用户的批量选择、搜索和移除。`POST /api/v1/admin/subscriptions/bulk-assign` 仍按 `plan_id` 与正整数有效天数逐用户分配，遵循既有套餐队列规则：每次成功创建一份生效中或待生效订阅，并非复用同一份订阅；逐项失败不会回滚其他用户已完成的分配。前端收到完整结果后按 `statuses` 的 `active` / `queued` 移除成功用户，仅对剩余 `failed` 用户使用新操作键。

批量分配的新前端始终发送 `Idempotency-Key`，后台对带键请求启用 `PreventReexecution`：已成功记录可重放，已有处理中、失败或过期记录不可重新取得执行权，返回 `IDEMPOTENCY_RESULT_UNCONFIRMED`，要求先核对已发放权益；协调器不可用时拒绝执行。响应使用计数、逐用户状态和有界错误摘要，`subscriptions` 为空数组，避免完整订阅 DTO 超过幂等响应容量。旧无键调用保留完整 DTO 及原分配行为。未知请求在同一标签页内持久保存原参数和键，前端不自动换键或过期重发；后端记录被 TTL 清理后、清除浏览器状态后或人工用新键另行提交不在这项有限幂等保护范围内，因此结果未知时不能直接重新分配。

## 兑换码

兑换码可发余额、并发或订阅权益，邀请码不从用户兑换入口产生权益。服务先做用户失败次数限制，再以代码级短期锁串行化请求；仓储在事务内锁定代码、校验状态/有效期/最大使用次数和“同用户一次”记录，并原子写入权益调整与使用记录。事务内的用户存在性与分组读取复用同一事务连接，避免持有事务时再次申请连接导致满载兑换请求互相等待。

每日活动可单独允许余额兑换码与管理员加款形成充值资格。来源开关默认关闭，仅对开启后的新增正数到账建立事件；在线订单内部兑换码排除，避免双计。管理员调整余额与原有调账记录同事务提交，设置余额按锁定后的真实增量计入。事件、历史及开关切换规则见[每日活动](daily_activities.md#daily_activity_eligibility)。

代码原文是用户凭据，查询或日志不能泄露批量未使用代码。已使用代码的类型、值、次数和套餐等核心字段不可通过批量编辑绕过一致性检查。支付充值生成的代码属于内部履约实现，必须保持订单专属且可识别部分执行后的重试。

## 领域不变量

- 外部“成功”只有在验签、订单/实例绑定和金额校验全部通过后才能产生权益。
- 订单保存下单时商品和提供商快照；后来修改配置不能改变历史订单语义。
- 所有回调、查单、人工 retry 和后台 reconcile 复用同一条件状态机与幂等履约入口。
- `COMPLETED` 表示内部权益已经发放，不仅表示提供商已收款；`PAID/RECHARGING/FAILED` 都仍需恢复处理。
- 订阅订单用 `source_order_id` 去重，余额订单用专属兑换码与 usage 去重；重复通知不能重复加款或发套餐。
- 额度重置点必须严格早于订阅到期，临期不足完整下一周期仍可刷新；各窗口按自身锚点推进，一次性日额度不得重复发放，重置次数按同一时间表幂等累计。
- 周期额度负责阻止新请求，不得让已经成功完成的普通请求因最终费用跨过剩余额度而免费；锁定订阅模式的溢出部分必须形成余额欠费，订阅用量不得超限，提交前预占仍须严格受限。
- 取消、超时和退款不能覆盖并发发生的真实付款，所有不确定状态优先查提供商而不是猜测。
- 权益变更后同步失效 Billing/API Key 认证缓存，并为状态、金额和操作者写审计记录。
