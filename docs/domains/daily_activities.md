# 每日活动

本文描述每日充值礼包、累计充值奖励、累计消费奖励的资格、随机入账、幂等领取与数据保留边界。活动不包含邀请奖励，也不修改支付渠道的到账规则或模型计费价格。

<a id="daily_activity_configuration"></a>
## 配置与累计起点

系统设置中的“每日活动”通过独立管理员接口保存 `settings.daily_activity_config`，默认关闭。三类规则分别包含独立开关 `enabled`、达标金额 `threshold` 与随机奖励上限 `reward_max`；独立开关缺省为开启，兼容升级前已启用的活动。金额最多两位小数，奖励范围为 0.10 至上限，包含端点。服务端使用密码学随机整数分抽取，每次直接增加个人余额。

`started_at` 在第一次开启活动时由数据库生成，客户端不能覆盖。首次开启前的充值、消费不补算；关闭再开启不会重置时间、累计进度或领取次数。关闭期间停止新领取，首次启用后的在线充值、真实消费仍持续累计。各活动独立停用只禁止该活动新领取，用户页隐藏对应卡片，不重置累计金额、已领取次数或历史；重新启用后按原累计资格恢复。已成功请求的幂等重放不受总开关或独立开关影响。公开设置与 HTML 注入仅增加 `daily_activity_enabled`，不公开管理配置；保存后触发现有设置缓存刷新。

另有 `include_redeem_balance`（计入兑换码余额）与 `include_admin_balance`（计入管理员加款）两个独立开关，默认关闭，旧配置缺字段也按关闭处理。只有活动已经首次开启、且对应来源开关开启时的新到账金额才记录资格，不补算旧流水；总开关暂时关闭时，只要来源开关仍开启，已启用活动的来源金额继续累计。关闭某来源只停止记录新金额，不删除已累计进度或未领次数，再开启继续新增累计。来源开关以入账事务读取到的设置为准，在途事务不会因稍后切换开关而重算。

每日礼包以北京时间 00:00 换日，按当日符合口径的到账金额达标，每天最多领取一次。充值和消费奖励使用累计金额，每达到一次门槛增加一次资格，未领取机会跨日保留。调整门槛后按新门槛重新计算累计资格，但已领取次数保留，不回滚已经发放的奖励。

<a id="daily_activity_eligibility"></a>
## 充值与消费口径

在线付款统计首次开启后已履约完成的余额充值和外部支付订阅订单，以 `completed_at` 为到账时间。余额充值保留本金 `amount - bonus_amount` 口径，排除赠金；订阅购买按订单 `pay_amount` 的数值直接累计，不做币种或汇率换算，也不改用套餐当前价格。站内余额支付（`payment_type=balance`）始终排除，防止充值再购订阅重复增加资格。两类金额都用于当日礼包和累计充值奖励；购买订阅本身不计模型消费。

曾履约成功且具有 `completed_at` 的订单保留原到账金额对应的活动资格，退款申请、处理中、退款失败、部分退款和全额退款均不扣减累计金额或可领取次数，也不追回已领取奖励。每日礼包仍按原 `completed_at` 所在的北京时间日期计算，不把金额挪到申请退款或完成退款当天。未履约完成的订单不因进入退款状态而获得资格。历史已退款订单只要原完成时间在活动首次开启之后，也按这一口径计算；活动首次开启前的订单仍不补算。此规则只改变活动资格统计，不改变原退款资金处理或权益回收。

可选来源使用独立的 `daily_activity_credit_events` 保存入账快照：

- 兑换码只接受实际兑换到账的正数余额额度，订阅、并发、邀请码、零额和负数不计入。多人兑换同一码按各人的使用记录分别归属，同一使用记录只能形成一个事件。
- 管理员通过余额调整入口加款按实际余额增加量计入；“设置余额”只计新旧值的正差额，减款或不变不产生资格，注册赠送与创建用户时的初始余额不计入。生产路径的余额修改、原有调账流水及活动事件同事务提交，任何写入失败都回滚，提交后才执行缓存失效和返利副作用。
- 在线订单用于内部履约的兑换码按 `payment_orders.recharge_code` 排除，无论订单处于何种状态，避免在线订单与兑换来源重复统计。活动奖励直接增加余额，不产生兑换/管理员加款事件，不会再次形成充值机会。

事件只保存来源、用户、金额、到账时间和使用记录标识，不保存兑换码原文，不依赖兑换凭据的级联删除。它与实际权益发放同事务成功或回滚；状态和领取都从同一份事件计算当天礼包及累计充值资格，当前来源开关关闭也保留已有事件。默认关闭或未首次启用时不记录；没有历史回填。

消费来自最终资金结算事务中的 `SubscriptionAmountUSD + BalanceAmountUSD`，写入独立 `daily_activity_spending_events`。普通请求、单张异步图片、批量图片、创作台和 Video 捕获均覆盖；预占冻结、失败释放、零金额结算以及奖励入账不计消费。团队请求按实际付款 Owner 归属，行为成员不重复获得资格。

消费事件与扣款同事务提交，以 API Key 和结算请求 ID 唯一去重。仅新插入的事件同事务累加 `daily_activity_spending_totals`，活动进度直接读取用户累计值，避免每次扫描全部历史。未配置、未首次开启、无有效起点时跳过记录，不改变原扣款；启用后的数据库事件或累计值写入失败使资金事务一起回滚，避免余额和资格只有一边成功。消费金额保留 12 位小数，不能提前按奖励的两位精度截断。

<a id="daily_activity_claims"></a>
## 领取与并发边界

用户接口只从登录会话取得本人 ID，不接受客户端指定领取金额、资格金额或其他用户。服务端每次重新读取配置和资格，先对配置加共享锁，再对付款用户行加 `FOR NO KEY UPDATE` 锁，与既有资金锁兼容。同一事务保存每次奖励记录、批次结果和余额变动，不调用会增加累计充值额的后台余额调整方法。

领取请求必须携带 `idempotency_key`。同一用户相同键重放返回原随机结果；改变活动类型或单次/批量方式返回冲突。前端先将请求号存入当前用户的会话存储，存储不可用时不发送领取；任何非成功响应均保留原键，避免超时后再遇登录失效而丢失原请求号。HTTP 成功但领取响应不完整或字段非法时也保留原键，只有校验通过的完整结果才能清除待确认请求；随后刷新状态或历史失败不会重新发放奖励。每日礼包另有用户与日期唯一约束。全部领取单批最多 100 次，剩余次数返回页面继续领取，不清空未领取资格。

提交后同时失效鉴权与余额缓存；断连后重放也执行缓存补偿。关闭活动不影响读取本人分页历史，也不影响已完成请求的幂等重放。历史按每次奖励独立展示时间、活动类型和金额。

## 用户页面与导航

每日活动入口紧随仪表盘，普通用户与管理员个人菜单顺序一致。每日礼包单独占第一行，充值与消费奖励在第二行平分；停用活动不展示，仅余一个累计活动时占满该行。用户卡片不展示随机奖励区间，历史明细保留实际领取金额。未确认领取在卡片隐藏后仍保留原请求号的确认入口，不因此生成新领取请求。

## 存储与接口

迁移 `300_daily_activities.sql` 新增活动配置、消费事件、用户消费累计表、领取批次和奖励明细；`301_daily_activity_credit_events.sql` 新增可选充值来源事件。它们是持久资金与资格记录，不属于可清理的使用日志或运行时数据；备份恢复时应与用户余额一起保留。清理 `usage_logs` 不影响活动资格。不能独立清空领取记录，否则会恢复已消耗的机会。

| 接口 | 权限 | 用途 |
| --- | --- | --- |
| `GET /api/v1/daily-activities` | 用户 JWT | 三类活动的独立启用状态、当前进度、已领与可领次数，以及两个来源开关状态 |
| `POST /api/v1/daily-activities/claim` | 用户 JWT | `activity_type`、`all`、`idempotency_key` 领取 |
| `GET /api/v1/daily-activities/history` | 用户 JWT | 本人历史，`activity_type` 筛选与 `page/page_size` 分页 |
| `GET/PUT /api/v1/admin/settings/daily-activity` | 管理员 | 独立读取/保存活动开关与规则 |
