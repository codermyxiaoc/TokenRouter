## 资源关系

| 资源 | 领域职责 | 主要关系 |
| --- | --- | --- |
| API Key | 客户端凭据和消费边界 | 归属付款用户，可选归属团队；普通 Key 指向一个分组，复合 Key 通过前缀映射到多个分组；可选择自动、指定订阅或仅余额的结算来源 |
| Group | 面向用户的产品/策略边界 | 指定平台、默认/独占状态、倍率、能力、回退、模型规则、RPM 和展示策略 |
| Channel | 多个分组共享的模型映射与定价目录 | 一个分组最多属于一个渠道；按分组、平台和模型解析映射、限制、计费来源与价格 |
| Account | 可实际调用上游的凭据和运行资源 | 通过多对多关系加入分组；保存平台、凭据、代理、并发、优先级、资格、配额和账号级模型配置 |
| Usage billing record | 一次不可重复应用的资金/额度变更 | 以 `request_id + api_key_id` 认领，绑定付款用户、行为用户、团队、Key、分组和账号 |
| Usage Log | 已完成请求的可查询事实 | 保存端点、模型链、token/媒体、金额和归属；用于统计与审计，不单独充当扣费账本 |

分组是客户端选择的产品边界，渠道是后台共享的映射与价格边界，账号是调度执行边界。三者不能合并成一个“供应商配置”：同平台分组可以有不同产品策略；一个渠道可以为多个分组提供差异化定价；账号又可以加入多个分组并在每次请求时接受独立资格检查。

普通 Key 的 `user_id` 是付款用户。团队 Key 同时携带 `team_id` 和创建/行为成员信息，结算命令中的 `UserID` 与 `ActorUserID` 必须分别表达付款 owner 与实际调用者。Key 自身还拥有状态、过期、总配额、滚动金额限额、IP 规则和模型重定向，不能只把它当作查找分组的随机字符串。

### API Key 结算来源

`api_keys.billing_mode` 与可空的 `preferred_subscription_id` 决定资金来源。历史 Key 和迁移默认值均为 `auto`，保持原有行为。

| 模式 | 运行时选择 | 额度不足或失效时的行为 |
| --- | --- | --- |
| `auto` | 当前分组可消费的订阅优先，之后使用付款主体余额 | 保留订阅与余额混合分配及余额兜底 |
| `subscription` | 请求准入只使用 `preferred_subscription_id` 所指的付款主体订阅 | 订阅不存在、到期、暂停、套餐不覆盖最终分组或预检时额度已耗尽则拒绝；已放行的普通请求若最终费用跨过剩余额度，订阅扣到上限，溢出部分扣付款主体余额并允许形成欠费，不得使用其它订阅 |
| `balance` | 只使用付款主体余额 | 跳过所有订阅解析与分配；不得因持有套餐改用订阅额度 |

创建或修改为 `subscription` 时，服务必须校验订阅属于实际付款主体且当前有效。个人 Key 使用本人订阅；团队 Key 使用 Team Owner 的订阅，成员自己的订阅不能被团队 Key 选择。套餐没有配置分组时表示不限制分组；配置了分组时，指定订阅 Key 的普通分组或复合映射只能取“原有用户权限与套餐分组”的交集。默认组、不可用分组回退、复合 Key 最终选组和 handler 的特殊回退都必须再次验证这一交集，不能仅依赖配置页面的过滤。

## 路由决策

路由从客户端模型到上游模型依次经过：复合 Key 选组、Key 级一跳重定向、渠道映射、分组/渠道限制和账号级映射。每层要保留输入与输出，形成 `requested_model`、`channel_mapped_model`、`upstream_model` 及去重映射链，供权限、计价、日志和响应元数据使用。

选定分组后，候选账号至少满足：

- 账号属于该分组，平台与强制平台一致，并处于可调度状态且未过期。
- 渠道和账号允许当前模型、端点与认证类型；需要时通过模型映射得到最终路由键。
- 账号具备特定能力或上游资格，例如图片、视频、Realtime、隐私设置、付费媒体或站点能力。
- 未被当前 failover 排除，未处于临时不可调度窗口，配额和限流状态允许继续尝试。
- 并发槽、等待队列、优先级/负载和会话粘性共同允许本次选择。

分组可以配置默认组、不可用回退组、客户端类型回退和模型优先账号列表，但回退后的目标仍要重新执行完整资格检查。API Key 允许在绑定分组不可用时回退到同平台默认分组的开关，也不能绕过用户权限、团队生命周期、渠道限制或账号能力。

OpenAI 兼容 Messages 在尚未向客户端提交响应时，会把管理员临时不可调度规则命中的账号错误提升为 failover，即使上游状态码本身通常不触发切号；命中模型范围的账号先写入模型级临时排除，再选择下一账号。请求内容或 Grok 内容策略导致的拒绝不进入这条通用账号错误路径。

OpenAI/Composite 分组可启用 `force_openai_fast`，使可信认证快照中的 OpenAI 请求在没有显式服务层级时也先形成 `service_tier=priority`，并覆盖客户端提交的其它合法 tier。该组级意图仍要经过全局 Fast/Flex 规则，系统过滤或阻断拥有最终裁决权；API Key 的 `force_off` 也可删除组级注入。字段仅对 OpenAI/Composite 分组生效，切换到其它平台或从不可信上下文读取时必须归零/忽略。

同一范围的分组还可启用 `free_openai_fast`。当最终使用的是 OpenAI 账号且计费档位为 `priority`/`fast` 时，网关保持发往上游的 Fast 档位不变，只用同一分组、渠道、长上下文和峰值规则重新计算 Standard 用户价格。Usage Log 的 `total_cost`、账号统计和账号额度继续保留 Fast 成本；`actual_cost`、余额/订阅分配和 API Key 配额使用 Standard 价格。缺少 Standard 定价时沿用既有缺价零成本记录路径，不把请求改写成普通上游请求；其它平台、普通档位和不可信认证上下文必须忽略该字段。

OpenAI 分组还可设置 `max_reasoning_effort` 与 `max_reasoning_effort_over_limit`。策略只处理客户端显式提供的 `reasoning.effort`、`reasoning_effort` 或 Messages 的 `output_config.effort`；缺省 effort 不会被桥接器补出的默认值误判为客户端请求。先按分组的模型范围映射（精确、前缀或后缀）得到有效档位，再比较 `minimal < low < medium < high < xhigh < max`：`downgrade`（默认）改写为上限，`deny` 返回本地 403 权限错误并标记为业务限制。推理档位改写仅能来自管理员配置的映射或上限策略，普通转发层不得再隐式改写；`none` 可作为映射和请求审计值，但不参与上限排序。Usage Log 同时保留策略前的请求档位与最终转发档位。复合 Key 在鉴权阶段已经选出具体 OpenAI 分组，因此沿用该分组策略；当前 fork 不重新开放 Composite 分组本身的推理配置。HTTP Responses/Chat、Messages 转换和 Responses WebSocket 的每个请求帧都必须执行同一裁决，且策略快照随 API Key 认证缓存传播。

Anthropic 分组也支持同一套模型范围映射、上限与超限动作，合法档位为 `low < medium < high < xhigh < max`，不接受 OpenAI 专用的 `none/minimal` 配置。Messages、Responses、Chat 三个入口都在协议转换和账号调度前执行策略；强制路由到其他平台时不套用 Anthropic 策略。兼容桥保留 `xhigh` 与 `max` 的区别，防止转换过程静默触发不同费率。

## 可用性与缓存

认证、分组、渠道和账号热路径使用缓存或调度快照降低数据库压力，但数据库配置和实时调度状态仍是权威来源。以下变更必须主动失效对应缓存或发布新快照：Key 状态/限额/映射变化，团队关系变化，分组平台/能力/倍率变化，渠道成员/映射/价格变化，以及账号状态、分组关系、凭据、代理、并发或资格变化。

渠道缓存同时保存分组的平台，用于按平台隔离渠道定价、模型映射和模型白名单。管理端修改分组平台时，必须在分组事务提交成功后立即失效并重建渠道缓存；平台未变化或更新失败时不得触发重建。否则这些查找会在缓存有效期内继续使用旧平台，定价还可能静默回退到内置价格。

“可认证”“可消费”和“可调度”是不同状态：

- Key 可认证表示凭据、用户、团队、IP 与资源归属有效。
- Key 可消费还要求标准模式下余额、订阅、Key 配额和滚动限额允许。
- 分组可路由要求产品策略允许该请求，并存在渠道/账号能力。
- 账号可调度还取决于瞬时并发、上游限流、配额、临时封禁和 endpoint 能力。

模型列表只能展示当前身份理论上可请求的模型集合，不能把瞬时没有空闲并发误报成永久无模型；真正请求仍要在调度时重新确认实时状态。

## 价格口径

一次请求同时存在用户扣费和账号成本统计两个口径。用户扣费的基础价格按分组逐模型定价、渠道定价、内置模型定价的顺序解析，再叠加分组和订阅/用户倍率；最终路由账号不能改变用户价格。分组逐模型条目支持 token、按次、图片和视频模式，命中后覆盖渠道与内置价格；条目自身的最终价格倍率和 Fast 模式倍率先在解析器中应用，再参与公开展示和结算。启用 `free_openai_fast` 时只把用户资金分配的基础金额切换到 Standard，不能把 Fast 的账号统计基数或 Usage Log 明细覆盖掉。账号 `rate_multiplier` 只影响账号维度的成本统计和账号额度累计，不应偷偷改变用户/API Key 扣款。

Kimi、Zhipu、DeepSeek 账号的计费候选不能把客户端 `claude`、`opus`、`sonnet`、`haiku` 名称送入全局 Claude/Sonnet 兜底价，因为兼容 Anthropic 请求不代表实际提供 Claude 模型。只有分组或渠道对该候选配置了显式价格时才保留；账号/渠道映射后的真实 CN 模型仍按正常优先级解析。候选全部被过滤或没有任何非空模型时返回 `ErrModelPricingUnavailable`，沿用零成本告警并保留 Usage Log 的既有路径，不得静默按 Claude 价收费，也不得因定价未知丢弃整条使用记录。

长上下文是模型或渠道的公开价格策略，不是账号能力。渠道存在有效 token 区间时，按总输入量命中显式区间，并禁止再叠加模型内置长上下文倍率；渠道区间是管理员明确配置的价格合同，不受分组长上下文开关影响。没有显式渠道区间时，分组 `long_context_pricing_enabled` 决定是否使用模型定价中的阈值和输入/输出倍率；新建和存量分组默认开启，显式关闭只去掉内置阶梯。分组 token 价卡只覆盖基础单价，其表单不把自定义区间当成长上下文阶梯。总输入量包含输入、缓存创建和缓存读取；各模型按自身边界语义判断是否进入长上下文档，进入后整次会话的输入侧与输出侧分别应用对应倍率。模型目录中的 `input/output_cost_per_token_above_*k_tokens` 会在加载时折算为阈值与倍率；条目显式提供任一 `long_context_*` 字段（包括 `0`）时以显式值为准。可选的 `pricing.override_file` 按字段浅合并覆盖目录和回退数据，`null` 删除字段，优先级高于两者；仅含完整价格字段的新模型才会被并入，拼写错误或只有局部补丁的未知模型会告警并丢弃。模型广场公开的上下文区间价格必须与相同分组倍率下的 `ActualCost` 一致，调度到任何普通账号或 Spark 影子账号都不能改变结果。账号 `extra` 中已废弃的 OpenAI 开关不参与判断；`long_context_billing_applied` 只在该规则实际增加费用时记录为真。

账号成本基数优先使用 Usage Log 的 `account_stats_cost`，仅在该字段为 `nil` 时回退 `total_cost`；显式 `0` 表示账号成本为零。账号统计和账号 `quota_used` 都把这个基数乘以账号 `rate_multiplier`，从而保持同一成本口径。用户余额、订阅和 API Key 配额始终使用 `ActualCost`，不受账号成本覆盖影响。账号成本回退到模型文件定价时，必须使用 Usage Log 最终记录的服务层级，并与模型长上下文倍率组合计算；自定义账号统计价格以及已经由 `ApplyPricingToAccountStats` 取得的用户计费结果都是最终成本基数，不得再次叠加服务层级倍率。

DeepSeek 默认价中的 Flash 输入/输出/缓存读取分别为每百万 token 0.15/0.60/0.003 USD，V4 Pro 保留 0.66/1.98/0.022 USD，再按同一 PricingAt 应用既有峰谷规则。2026-09-15 核对[官方定价说明](https://api-docs.deepseek.com/quick_start/pricing/)后，未采用上游 v0.2.5 已过时的 9 月 14 日 Pro 自动按 Flash 计费规则；后续结算和历史事实分开，不重算既有账单。分组和渠道显式价（含零价）不经过官方默认三价覆盖。现有目录解析尚未区分 `pricing.override_file` 中 DeepSeek 三价的字段来源，不能用该文件代替分组/渠道合同价来保证绕过 DeepSeek 官方默认价策略。

渠道模型定价显式声明计费模式和计费模型来源：

| 维度 | 可选语义 |
| --- | --- |
| 计费模型来源 | 客户端请求模型、渠道映射模型或最终上游模型 |
| 计费模式 | token、按次、图片、视频等，由对应价格字段和区间验证约束 |
| token 桶 | 输入、输出、缓存创建、缓存读取及适用的图片输出 token |
| 倍率 | 系统默认、分组、用户覆盖、订阅计划分组倍率、高峰因子及媒体独立倍率 |

计费来源为上游模型时，要在账号选定并完成最终映射后才能确定价格；模型限制与计费必须使用同一解析结果。高峰倍率按请求结算时刻和配置时区计算，只叠加到适用的 token 价格；图片/视频按次的独立倍率遵守各自规则。所有价格和倍率必须拒绝负值，并在配置写入时校验所选模式所需字段。定价模式冲突检测必须复用定价缓存键的归一化：忽略首尾空白，并把 `claude-*` 名称中的点号与连字符视为等价，防止两个配置静默覆盖同一缓存项；模型映射缓存只做小写归一化，不能套用这条定价专用规则而误报冲突。

渠道模型定价可为 token 模式配置 `time_pricing`：使用 IANA 时区和每日重复的左闭右开 `HH:mm`/`HH:mm:ss` 区间，倍率必须有限、至少 `0.01` 且最多两位小数，区间不得重叠；结束时间 `00:00` 表示当天 24:00，跨午夜区间必须拆成两段。该倍率只作用于渠道 token 的输入、图片输入、输出和缓存价格桶，不作用于按次、图片或视频模式，也不复制到分组价卡或账号统计规则。管理员写入时由后端最终校验，存储在 `channel_model_pricing.time_pricing` JSONB；当前 fork 的迁移文件为 `249_channel_model_time_pricing.sql`。普通请求使用结算时刻，OpenAI WebSocket 使用对应 turn 开始时刻；配置损坏或无法加载时安全回退到 `1x`，不改变既有计费。

Token 计费支持 `reasoning_effort_multipliers` 按 `none / minimal / low / medium / high / xhigh / max` 配置有限正数倍率，优先使用最终转发档位的显式值。未配置该档位时保持旧规则：旧 `max_reasoning_effort_multiplier` 仍有效，Fable 5.1 的 Max 默认 `3x`，其他档位默认 `1x`；显式 `1` 可以取消加价，未指定档位不等同于显式 `none`。这项扩展不会改变已有显式价格、免费价和旧 Max 字段。倍率作用于全部 token 成本桶，并与当前价格、服务层级、区间及分时倍率组合；按次、图片/视频按次和搜索附加费用不乘此倍率。请求经策略降档或协议转换后按实际出站档位结算；Gemini 只读取最终 thinkingLevel，不从预算 token 数推断档位。账号统计使用模型文件默认价时沿用原有最终档位规则，自定义统计价保持独立最终成本，`ApplyPricingToAccountStats` 复用已算出的 `total_cost`，均不重复叠加。旧渠道字段通过迁移 268 持久化，新映射通过 `287_channel_reasoning_effort_multipliers.sql` 增加空 JSON 字段，不批量改写旧价卡或分组 JSON；账号统计规则继续拒绝配置这两种推理倍率。渠道与分组表单可编辑各档位，模型广场展示配置后的有效倍率。

缓存写入可选地拆成 `cache_write_price`（5 分钟）和 `cache_write_1h_price`（1 小时）两档；1h 列为 NULL 时继续把旧列用于两档，保证历史渠道和账号统计规则的结算不变。该字段同时适用于渠道默认价、token 区间和账号统计价，显式 0 仍表示免费；分档用量缺失时按旧聚合 token 数回退。数据库迁移为 `261_channel_cache_write_1h_pricing.sql`。

Grok 媒体、搜索和 Voice 使用独立计价维度。视频按输出秒计价，`video_model_prices` 可按规范模型族与 480p/720p/1080p 覆盖，未命中时依次回退 `video_price_*` 和模型族内置价；异步创建不扣费，首次完成观察才用任务级稳定 request ID 结算。搜索以 `search_price_per_1k` 按调用次数附加在 token 费用之上；独立 `/web_search` 和 `/x_search` 的纯工具请求也可单独结算。Realtime、TTS、STT 分别使用每分钟、每百万字符、每小时价格；Realtime 握手或纯文本会话不出账，只有任一方向观察到非空音频负载后才按该连接的会话时长结算。未知的数字版 Grok 文本模型可以回退到当前默认文本 token 价，但模型 ID 含 `imagine`、`image`、`video`、`audio`、`speech`、`tts`、`transcribe` 或 `realtime` 时必须排除这项兜底；`vision` 多模态对话仍按 token 计费。上述列 `NULL` 表示使用默认值，显式 `0` 表示免费，不能用“缺少 token usage”跳过已确认的媒体或工具用量。

<a id="video_price_snapshot"></a>
### 独立 Video 定价与快照

Video 平台价卡支持 `video`（美元/秒）、`video_token`（美元/百万 Token）和 `video_per_request`（美元/成功任务）模式。渠道与分组逐模型价卡以 `video_prices` 数组保存 `resolution` 和 `price`，每个规范化分辨率只配置一个单价，不区分有无参考视频输入。数字分辨率规范化为数字加 `p`，支持 480p、720p、1080p 及显式配置的其它数字档位；厂商原生 `2K`/`4K` 保留为独立的 `2k`/`4k`，不隐式映射为 1080p 或 2160p。价格为零表示免费，缺少目标档位、价格为空或非法时不可报价。

旧价卡的 `has_reference_video` 字段保留读取兼容。同分辨率旧双行按一档处理，优先原无参考行，仅有含参考行时保留该行单价，显式零价有效；不按请求内容切换价格。后台表单加载时合并旧行，保存时仅提交分辨率和单价，空输入不变成免费价。后端继续识别旧双行以免历史配置失效，同条件重复、无效分辨率或非法价格仍被拒绝。此更新不批量修改数据库和已有任务快照。

`video_per_request` 只允许 Video 平台，使用矩阵或 `video_fallback_price`，不借用聊天 `per_request_price` 或历史 Grok 按次语义。它沿用视频价卡优先级、倍率和固定参考图附加费，单任务基础视频费用为一份有效单价；不能携带 Token 秒价预扣开关，也不依赖时长或 Token。只有纯兜底按次价卡允许省略分辨率，有矩阵时仍严格要求分辨率。现有 VARCHAR(20) 和 JSON 快照可容纳新模式，无需新迁移或批量更新已有数据。

价格优先级为分组逐模型视频价卡、分组专属秒价、渠道视频价卡。显式指定 Token 或按次模式会跳过秒价；匹配到分组逐模型价卡后即以该完整合同为准，缺档不穿透到渠道。可选 `video_fallback_price` 仅在该规范化分辨率不存在任何配置行时生效，支持只有兜底价而没有分辨率价的价卡。兜底使用同一计费模式、单位和正常视频倍率，显式零价有效。没有配置时返回明确缺价错误，不使用 Grok 的默认档位、默认秒价或时长上限。旧 Grok 路径和历史显式秒价保持兼容。

`VideoPriceQuote` 保存版本、计费模式、来源、模型、分辨率、原始单价、价卡倍率、有效单价与视频倍率，可随任务持久化，并记录是否使用兜底价。遗留参考视频标记仍可作为输入信息读取，不参与新任务选价；升级前已冻结的单价继续有效。有效视频倍率沿用 Grok：开启视频独立倍率时使用该倍率，否则使用调用方提供的有效分组倍率。结算仅按快照和可信用量计算，`TotalCost` 为价卡倍率后的基础成本，`ActualCost` 再乘视频有效倍率；异步预留可按基础成本分配不同订阅和余额倍率。修改价卡不改变已有快照。新 Token 任务在终态使用创建时价卡与资金模式、当时可用订阅及其套餐覆盖倍率；组/余额和独立视频倍率仍使用创建快照。限额和幂等规则见[视频任务结算](video_tasks.md#video_task_billing)。

Video 用户 Token 价卡可开启 `video_token_prepay: {"price_per_second": 0.3}`；`null` 为关闭，显式零秒价有效。此字段与最终 Token 价独立，克隆、渠道价格倍率和市场展示均保留原始固定值，绝不叠乘渠道、分组、独立视频、套餐或用户余额倍率。预扣是秒数乘固定单价再加固定图片费，完成后按真实 Token 费用退补差。前端从 Token 切换到其它计费模式时清空该配置；后端拒绝非 Video Token 卡携带它。账号成本统计规则拒绝用户预扣与兜底价配置。

Video 用户价卡可配置 `video_image_input_pricing: {"free_images": 5, "price": 0.15}`，表示前 5 张免费，只对超出的参考图片按美元/张收费；`free_images: 0` 表示从第一张收费，省略或 `null` 表示关闭。单价必须明确且有限非负，显式零价有效。配置跟随上述完整价卡优先级，不从低优先级价卡拼接附加费；账号统计规则不接受这一用户附加价。图片数量由实际协议的输入参数确定，无法可靠计数时仅开启附加费的请求拒绝报价，关闭时维持原兼容性。

配置附加费后，计算为 `max(输入张数 - 免费张数, 0) × 固定单价`，不乘渠道价格倍率、视频/分组倍率、套餐覆盖倍率、用户余额倍率。创建时冻结单价、免费张数及输入张数；供应商输出图片和配置修改不能改变它。此时 `CostBreakdown.OutputCost` 记录视频基础费用，`ImageInputCost` 记录固定附加费，`TotalCost` 为二者之和，`ActualCost` 为视频应用倍率后的金额加固定费。使用记录的用户倍率只描述视频部分，图片费单独列出。上游账号成本继续使用既有总基础成本乘账号倍率的独立统计口径，不参与用户扣费。模型广场单独展示固定单价。分辨率编辑器仅显示已配置或手动新增的档位，空价卡不预填 480p/720p/1080p。

视频 Token 使用独立用量指针：缺少可信 usage 是未能结算，显式可信零 Token 才能算出零视频费用。秒数必须为有限正数，不截断长视频，不从负数或缺省值推断时长。聊天长上下文、服务层级、推理档位和分时倍率不自动应用于视频 Token。渠道矩阵通过 `289_video_token_pricing.sql` 增加 JSONB 列，图片附加费通过 `292_video_image_input_pricing.sql` 增加可空 JSONB；`293_video_fallback_and_token_prepay.sql` 增加可空兜底价及预扣配置，旧行默认关闭。分组价卡沿用已有 JSON 存储，不批量改写旧定价。

<a id="usage_settlement"></a>
## 用量结算

`recordUsageCore` 统一归一化供应商用量、确定计费模型、解析订阅和倍率、计算成本并构造 Usage Log。`simple` 运行模式不执行资金扣款，默认只尽力写日志；显式开启密钥消费窗口限制后，通过同一持久幂等仓储仅累计密钥 5h/1d/7d 窗口，不动余额、订阅、团队、账号及平台额度。`standard` 模式必须调用统一结算仓储。

标准结算流程为：

1. 要求非空 `request_id`，规范化 `UsageBillingCommand`，并根据归属、用量、价格和可选请求 payload 摘要生成指纹。
2. 在 PostgreSQL 事务中插入 `(request_id, api_key_id)` 去重记录；已有相同指纹表示请求已应用，已有不同指纹则返回冲突而不是再次扣费。
3. 先以 `FOR NO KEY UPDATE` 锁定付款用户，之后按稳定顺序读取并锁定可用订阅，避免同一用户并发消费穿透限额。
4. 按 Key 的结算模式分配资金：`auto` 先分配适用订阅后扣余额，`subscription` 只锁定并分配指定订阅到额度上限，已放行普通请求的溢出部分按余额倍率记为欠费，`balance` 跳过订阅并只扣余额；结果保存订阅与余额各自金额和有效倍率。
5. 在同一事务内累计团队成员周期用量、API Key 总配额和滚动窗口；账号额度使用 `COALESCE(account_stats_cost, total_cost) × account_rate_multiplier`，其中显式零成本不累计额度。
6. 提交成功后返回 `Applied`、新余额、订阅分配和账号/Key 配额状态；遇到 PostgreSQL 死锁时由外层开启新事务做有界重试。

`users.balance`、API Key 配额和窗口用量使用 `NUMERIC(20,8)`。进入这些 SQL 加减法前，金额必须按 PostgreSQL 一致的 half-away-from-zero 规则统一量化到 8 位；否则同一笔第 9 位处于 half 边界的金额会因余额减法与配额加法方向相反而产生 `1e-8` 对账差异。幂等指纹仍由量化前的原始金额派生，避免升级前后的同一请求重试被误判为冲突；10 位精度的订阅与用量事实不应在命令入口被提前降到 8 位。

订阅解析必须同时满足生效时间、状态、周期额度和分组覆盖范围。`auto` 没有适用订阅时才走余额倍率，并允许订阅与余额共同承担；锁定订阅模式在请求准入时不允许回退其它订阅或余额。普通请求已经通过预检并成功完成时，如果最终费用超过指定订阅的剩余额度，事务只把可覆盖部分累计到该订阅，订阅用量保持封顶，溢出基础用量按余额倍率扣减付款主体余额并允许余额为负，防止后置结算失败形成零计费记录。该余额扣减只结算已放行请求及并发在途请求，不会把额度已耗尽的指定订阅 Key 转成按量模式；后续新请求仍按订阅快照拒绝，即使用户余额足够也不回退。指定订阅不存在、失效或不覆盖最终分组时，整笔结算仍须失败，不能伪装成余额扣费。结算命令和幂等指纹都携带模式及指定订阅 ID，避免异步记录阶段因 Key 配置后来变化而选择错误资金来源。团队请求锁定和扣减的是 owner 对应付款用户，但团队成员累计使用 `ActorUserID`，避免账务与行为归属混淆。

批量图片使用独立的预占/结算命令：提交时持久化余额与订阅分配快照，完成或取消时按同一幂等 request ID 结算、释放差额或回滚适用预记。指定订阅必须在提交上游前完整覆盖预占金额，额度不足就回滚并拒绝，不能复用普通请求“上游完成后再把溢出记为余额欠费”的时序。

固定价的第三方异步 Images 同样要求上游调用前足额预占，但使用独立图片账本而非批量任务表。普通结算及预占都分别解析订阅与余额倍率，不能从当前订阅的 `ActualCost / TotalCost` 推导余额倍率；图片独立倍率（含显式零价）禁止被套餐倍率覆盖。Token 计费继续叠加高峰因子，固定媒体价格不叠加；显式零高峰也不能被缺省值恢复为收费。异步图片的冻结报价、失败释放、结果不明及实际费用超预算的边界见[异步图片资金预占](media_tasks.md#async_image_billing)。此项只保护升级后的新预占请求，不回填历史扣费或调整存量余额。

Seedance 原生视频使用完成查询返回的真实输出 token 计费，创建时仅保存资金选择与模型快照，不预占未知视频费用。其任务归属、查询触发、订阅约束和 Redis 留存边界见 [Seedance 计费](../interfaces/seedance_upstream.md#seedance_billing)，不能套用批量图片的预占语义或 Grok 视频的按秒价格。

## 记录与对账

用量费用明细使用八位小数展示，站内余额单位换算与美元账号成本分别沿用各自 formatter，不改变存储精度或结算金额。用户 CSV 导出在开始时固定筛选、排序和文件日期并复用于全部分页；这只保证查询参数一致，不代表导出期间的数据库事务快照。

普通网关在资金事务成功后才尽力写 Usage Log。日志写入失败不能回滚已提交的扣费，也不能因重试日志而再次扣费；反过来，结算失败时不得写一条看似成功的正常使用记录。`usage_billing_dedup` 和实际余额/订阅/配额更新是资金效果的幂等边界，Usage Log 是分析、用户账单展示和运维排查的事实视图。

Usage Log 应保存付款用户、行为用户/团队、Key、账号、分组、请求 ID、入口/上游 endpoint、平台、模型链、计费来源、token/媒体明细、基础成本、实际成本和 billing type。管理端用量明细可从列设置启用默认隐藏的请求 ID 列，并直接复制完整值用于跨日志排障；升级旧列偏好时只追加该列的默认隐藏状态，不覆盖管理员已有选择。增加新协议或用量桶时，需同时更新协议解析、成本计算、结算指纹、日志 schema、聚合查询与对账测试。

用户端和管理端使用记录在费用前默认显示“计费类型”，可由各自列设置隐藏；用户 CSV 与管理端 Excel 导出使用同一显示规则。优先读取本条记录的 `subscription_amount_usd`、`balance_amount_usd`：两项都大于零显示“订阅＋余额”，仅一项大于零显示对应的“订阅扣费”或“余额扣费”。没有正数分配且 `actual_cost=0` 时显示“未扣费”，不据此猜测免费、缺价或结算失败；历史记录缺少分配明细时回退该记录的 `billing_type`（`0` 余额、`1` 订阅），无法识别则显示“未记录”。显示不读取密钥当前的结算配置，也不改变资金结算、统计或筛选行为；现有订阅筛选仍包含混合扣费记录，因为其持久化类型同为 `1`。

模型明细与模型分布使用不同但可追溯的展示口径：`requested_model` 保留客户端提交的名称，包括复合 Key 前缀和 Key 级别名；模型分布的请求维度使用完成复合选组和 Key 级重定向后的内部请求模型 `model`。因此用户自定义名称仍可在单条记录和映射链中审计，但不会把相同内部模型拆成多个分布项；上游和映射分布继续分别使用实际上游模型以及“内部请求模型 -> 上游模型”。

<a id="usage_video_pricing"></a>
### 视频用量计价展示

管理员和用户的计费模式筛选共用渠道定价文案，依次展示 Token、按次、图片（按次）、视频（按秒）、视频（按 Token）、视频（按次），提交值仍为既有六种后端枚举。选择视频按秒时提示同时包含未细分计费单位的视频记录：`video` 仍兼容 Grok 等未区分单位的记录和历史空值视频，不能仅凭该筛选把明细标签或历史账目改为按秒计费。

用户和管理员使用记录共用视频展示契约。基础 DTO 保留记录中的 `video_count`、`video_resolution` 和整数 `video_duration_seconds`；独立 Video 已结算任务另补只读 `video_billing`，包含历史计费模式、单位、单价、分辨率、精确时长和可信 Token 数，参考视频标记仅保留兼容数据，不作为价格条件展示。新写入的计费档位只包含分辨率，旧记录不迁移。读取使用 `video_capture:<任务 ID>` 与行为用户、原 API Key 同时关联已结算任务，不能用团队付款主体替代行为用户。列表按页批量读取任务中的 Quote 和 Metadata 子对象，普通记录不增加此查询；返回值只含计费白名单字段，不暴露任务正文、媒体地址或凭据，不改变任何扣费或任务状态。

历史单价只能来自任务冻结的 Quote，不从当前渠道、分组价格或总费用倒推。缺失、损坏或缺少显式单价的快照不补详情，明确零价仍有效。时长优先采用 Metadata 中的精确秒数，避免将 2.5 秒的真实用量显示为日志兼容整数 3 秒。具有明确单位的记录分别显示“视频（按秒）”“视频（按 Token）”或“视频（按次）”，费用浮层分别列秒价与时长、每百万 Token 单价与 Token 数、单次价格与一次计费；按秒和 Token 视频总费用不显示为“单次价格”。`video_per_request` 筛选独立新增，旧 Grok 按次视频也可能保存为 `billing_mode=video`，没有可靠单位快照时只能中性显示“视频”，不把它推定为按秒；旧筛选值和持久化模式不变。

参考图片展示区分未知与零：已知输入张数可以单独显示，只有存在完整历史图片价卡时才展示免费额度、计费张数、固定单价和实际图片费。免费额度是价卡阈值，不是本次实际免费张数；计费张数为 `max(输入张数 - 免费额度, 0)`。图片费直接取本条记录的 `image_input_cost`，独立列出且不乘视频或分组倍率，不能混入视频秒价或 Token 单价。用户 CSV 沿用相同计费模式标签，后台 Excel 列结构保持原样。已有任务快照可直接补全历史展示，无需回填账务数据。

### 实际扣费套餐展示

使用记录查询返回只读的 `billing_subscriptions` 摘要，包含订阅 ID、套餐 ID、可用的套餐名称与该订阅承担的金额。摘要从记录自身的正数订阅分配生成，同一订阅重复分配汇总；一次请求扣取多个订阅时全部保留，订阅与余额混合扣费时仍保留原计费类型。没有分配明细的历史记录仅在有实际费用和自身订阅 ID 的情况下兼容还原，不从 API Key 当前绑定或用户当前有效套餐推断历史扣费。

套餐名称优先读取对应来源订单中匹配套餐的名称快照，缺少快照时按记录中的套餐或订阅关联查找套餐名称，查询兼容已软删除记录；无法找到名称时显示订阅 ID。名称回退到套餐表时反映当前名称，不承诺还原改名前的历史名称。该展示不改变结算事务、金额、扣费顺序或存储结构。用户和管理员使用记录及其导出采用同一摘要。

错误请求只能在权限范围内按内部请求关联 ID、API Key 和付款主体匹配已保存的使用记录，再展示实际扣费套餐；失败尝试恢复成功时展示最终实际结算所用套餐，不能取失败分组或密钥预选订阅代替。没有可关联记录时套餐留空，不能据此断言未扣费，因为使用记录可能异步写入、已清理或未保留。错误页访问范围仍遵守原有用户归属校验，见[恢复错误的查询与归属](../operations/ops_monitoring_and_alerting.md#recovered_error_visibility)。

## 领域不变量

- 分组定义产品策略，渠道定义共享映射/定价，账号定义执行能力；任何一层的 ID 都不能代替另一层。
- 客户端模型、渠道映射模型和上游模型必须分别保存，限制、计费和响应恢复使用明确来源。
- 缓存只能加速决定，不能让已禁用的用户、团队、Key、分组或账号继续工作。
- 标准模式的资金、订阅、团队成员、Key 和账号额度效果必须位于同一幂等事务。
- 公开长上下文区间价格必须等于实际用户扣费单价；账号选择和账号 extra 不能改变用户价格，渠道显式区间不能重复叠加模型内置倍率。
- 账号统计和账号额度必须使用同一成本基数与账号倍率；用户资金和 API Key 配额仍只使用 `ActualCost`。
- 指定订阅 Key 的最终路由分组必须被套餐覆盖，预检发现订阅失效或已耗尽时不得放行或静默回退；已放行且成功的普通请求由订阅承担到上限，溢出部分必须形成余额欠费，不能结算为零或把订阅用量扣超。
- `request_id + api_key_id` 相同但指纹不同是冲突，不是可忽略的重复请求。
- Usage Log 不是扣费事务的提交标志；对账必须以去重记录和账户/权益效果为准。
- 新增计费类型时，要覆盖订阅与余额混合分配、团队归属、重复提交、死锁重试和日志失败测试。
